## 3. 计算估计：先标定，再承诺

2026-10-28旧CPU参考，每作业训练步中位数跨种子均值约：batch16=1.29秒、64=4.55秒、196=15.83秒。它们不是新诊断实测；新脚本还会读Oracle梯度、评价B池、记录和加载，不能直接把这三个数字当总时长。

执行前在实际设备检测CPU/GPU、PyTorch/PyG、FP64支持与峰值内存。默认先用5个单线程CPU worker；GPU可用也先做D0数值一致性，不默改精度。

标定使用固定最小块（非按效果挑选），记录：
t_query、t_solve、t_oracle_A、t_grad_B、t_eval_B、t_clone_step、T_IO，以及中位数／P95、冷启动与稳定期。标定若读取开发标签，也必须记录为该实验pilot，不能假装未看过；不据此改变成功阈值。

| 项目 | 核心逻辑量 | 可复用项 |
|---|---|---|
| D1 | 360次几何构造；TRUE＋3PERM＋3RAND等控制 | 同块V/核/W、45个g_B |
| D2 | 180块×12非冻结臂×3η＝6480临时步 | θ/B基准、源梯度、D1反馈 |

粗略CPU worker-seconds：
C_D1 = 360(t_query+t_oracle_A) + 45t_grad_B + 360t_controls + T_IO；
C_D2 = 6480(t_clone_step+t_eval_B+t_eval_A) + T_IO；
C_D3 = 360t_geometry + 5400t_solve + T_IO。
先剔除真实可复用部分，再按实际并行度估墙钟，乘1.3缓冲。不能只除以物理核数或把所有标签／块当并行独立作业。

每包建议先设8小时墙钟硬上限，实际冻结预算由执行时的标定与用户授权范围决定；这是规划上限，不是本次已经授权／消耗8小时。8小时不足则在启动前缩小工作包，不悄悄减种子、目标batch或成功门槛。监控50%提醒、80%需续预算、100%停；未获追加时不把预算耗尽记成研究成功。

文档撰写本身不启动任何这些作业。代码开发时间与训练／诊断计算时间分开估算；不把历史复用成本记成本轮新训练。

## 4. 冻结、执行与变更

1. 实现新增接口，D0通过；将实际执行代码提交。配置、数据角色和本方案生成SHA清单。
2. 为每包生成run_id、job_matrix与预算。缺少的必需臂不能静默跳过。
3. 在读取诊断标签前封存未使用目标标签计算的各块θ／V／W配置；若流式构造，则每块先seal再调用Oracle并写事件顺序。
4. 按预定顺序运行；每项先保存逐块原始数据，再汇总、画图、判断。
5. 新增假设另建amendment：时间、原因、在此之前看过哪些指标、改了哪些条件；不能覆写冻结计划。
6. 正常适配作业仍需整包封存后才评价development标签。不得因为新诊断可以读dev，就让训练回调也读dev。
7. 完成后更新文档和实验状态，保存来源与哈希，再按项目约定提交、推送GitHub并核对远端提交。
8. 工程失败、自适应算法失败、统计证据不足、预算不足分别记录。

## 6. 不得混淆的结果

- D0测试通过 ≠ D1方向正确。
- D1同批梯度正确 ≠ D2另一批目标改善。
- D2一步改善 ≠ D9长期分类改善。
- 代理风险下降 ≠ 标签监督迁移。
- 合成成功 ≠ 真实域条件稳定。
- 跨两个已观察的数据集复核 ≠ 新盲测或最终泛化证明。
